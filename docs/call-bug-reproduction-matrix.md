# Матрица воспроизведения багов звонков

Что можно проверить на текущем стенде (два эмулятора, Maestro, Kotlin/Vitest),
что требует реального OEM-устройства, а что — `google-services.json` (FCM).

Источник данных: `scripts/triage-call-reports.mjs` по 431 открытому репорту,
из них 63 про звонки. Цифры в скобках — число репортов в кластере.

## A. Воспроизводимо сейчас — эмуляторы, без FCM и без устройств

| # | Симптом | Репорты | Чем воспроизводится |
|---|---------|---------|---------------------|
| A1 | Кнопка «принять» сбрасывает звонок или не срабатывает | #1268, #1108 (кластер accept-button, 6) | Звонок A→B между эмуляторами, быстрый тап по «принять». Гонка в `answerCall` — защита от двойного тапа уже есть (WEE-45), но репорты продолжаются |
| A2 | Отклонённый звонок продолжает звонить | #1232 (2) | Отклонение из UI приложения воспроизводится; отклонение из шторки уведомления — нет (см. C) |
| A3 | Одновременно установленные Bastyon и Forta дублируют звонки | #847, #809 (3) | Логика дедупа (`incoming-call-dedup`, `call-push-dedup`) покрывается юнит-тестами; полный сценарий требует APK Bastyon |
| A4 | Экран гаснет во время звонка и не включается | #1281 (1) | Логика proximity wake lock в `CallActivity`; поведение самого датчика — только на устройстве |
| A5 | Индикатор громкости перехватывается в начале звонка | #1216 (1) | Привязка кнопок громкости к `STREAM_VOICE_CALL` |
| A6 | Размер видео в веб-версии | #936 (1) | Обычный браузер, к Android отношения не имеет |
| A7 | Тыловая камера в миниатюре отображается неверно | #939 (1) | Эмулятор отдаёт синтетическую камеру — проверяется логика выбора, не картинка |

## B. Требуется реальное OEM-устройство (Xiaomi/Samsung/TECNO/Realme/Huawei)

Аудио-тракт: 24 репорта (`no-audio` 4, `stuck-after-call` 22, `speaker-toggle` 5,
с пересечениями). Эти дефекты живут в коде вендорской прошивки — на образах
Google (эмулятор, Pixel) соответствующего кода нет, воспроизвести нечего.

- Сломанный аппаратный AEC → тишина или эхо
- Застревающий глобальный флаг mute микрофона → «меня не слышат»
- Асинхронный сброс `MODE_IN_COMMUNICATION` через 1–5 с → односторонний звук
- MIUI privacy shield → `AudioRecord` молча пишет тишину
- Игнорирование обоих API переключения динамика → «звук не переводится на динамик»
- Убийство процесса энергосбережением → телефон остаётся в режиме разговора

**Важная зацепка:** 6 из 24 аудио-репортов — с устройств **вне** вендорского
гейта `VendorAudioPolicy.BROKEN_HW_AEC_VENDORS` (OnePlus ×2, Vivo, Samsung и др.).
Это довод за то, что гейт по списку вендоров нужно заменить на runtime-детект.

## C. Требуется `google-services.json` (FCM) — зафиксировано

Единственный кластер, который **невозможно** проверить без него, потому что без
FCM телефон просто не узнаёт о звонке, пока приложение закрыто.

| Симптом | Репорты | Почему нужен FCM |
|---------|---------|------------------|
| Входящий не приходит, когда приложение закрыто или в фоне | кластер `background-incoming`, 22 | Событие доставляется только push-ом |
| Звонок приходит с задержкой | часть тех же 22 | Замеряется `deliveryLatencyMs` из FCM |
| Дубли входящих (звонит дважды) | часть #847, #809 | Гонка «FCM против Matrix-sync» |
| Отклонение из шторки уведомления не гасит звонок | #1232 | Уведомление создаётся FCM-сервисом |
| Протухшие приглашения (TTL) | телеметрия | `InviteThrottleGuard` живёт в FCM-пути |
| Звонок при убитом процессе (cold start) | часть 22 | Процесс поднимает FCM |

Итого: **22 из 63** репортов про звонки закрыты без FCM быть не могут;
остальные 41 — можно.

## Ограничение классификатора

25 репортов попали в `other`, и часть из них по тексту — про звук
(#1292 «собеседник меня слышит, я его нет», #1273, #1210). Ключевые слова
классификатора их не поймали. Список выше по этой причине занижает аудио-кластер;
уточнение словаря — отдельная небольшая задача.
